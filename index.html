The enemy on your screen is 133 milliseconds old

Your phone draws everything else where it was at least 133 ms ago, while the server judges collisions where things are now. How one open-source Rust server closes that gap, and where it still doesn’t.

By Vitalii ErmolaevSeptember 202613 min read

You are a small dot in a maze, and a bigger dot is coming for you. On your phone there is a clear strip of floor between the two, a gap about two-thirds as wide as your own dot. You turn away. You die anyway.

Nobody cheated. The server did what most game servers do. At tick 5,112 it measured 17 pixels between you and the enemy, saw that this was inside its 20-pixel kill distance, and sent you a death event. Every number in that decision was correct. But the enemy on your screen was not the enemy at tick 5,112. It was the enemy at tick 5,104, drawn 8 ticks late on purpose so that it would move smoothly.

Every real-time multiplayer game has a gap like this between what the server knows and what the player sees. Shooters settled half of the problem two decades ago: when you fire, the server rewinds the world to what you saw and checks the hit there. Kills by contact rather than by a trigger pull (being caught, run over, eaten) are more often decided on server time, and players experience them as “that didn’t even touch me.”

I spent a good part of the past year on this in the backend of a small mobile arena game. The result is fairtick, an authoritative game server in Rust built around one rule: if a decision depends on what a player saw, the code has to name the timeline that player saw and use it. When one player eats another, the attacker’s client files a claim describing what it drew, and the server checks it against its own recorded history. When a server-controlled enemy catches a player, the victim’s client files the claim instead. Bots, which have no screen at all, are the exception I haven’t solved. The code is dual-licensed under MIT and Apache 2.0.

Two clocks, one kill

A game client runs on two timelines at once. Your own dot is predicted: the client applies your input immediately and reconciles with the server afterward, so your dot lives slightly ahead of the authoritative state. Everything else is interpolated. The server sends snapshots 30 times a second, and to draw an enemy smoothly the client needs two of them to blend between, so it deliberately renders other entities in the past. In fairtick’s reference client, that delay is at least 8 ticks, or 133 ms at 60 ticks per second, and it grows to as much as 18 ticks on a jittery connection.

Enemies move at 100 pixels per second. (These are world pixels, the unit the server works in; your dot is 18 of them across.) Eight ticks of delay puts the enemy you see 13.3 px behind where the server has it, and two dots touch on screen when their centers are 18 px apart. So the server measures 17 px and kills, while your screen shows 30 px and a 12 px gap.

This isn’t a thought experiment. Before fairtick changed its rules, device telemetry showed deaths landing when the server measured 10 to 13 px while the player’s screen showed the enemy 26 to 28 px away.

Interpolation is doing its job here; it is what keeps remote movement from stuttering. The mistake is deciding something the player has to see, a collision, on a timeline the player never saw.

The fixes that don’t fix it

The first thing everyone reaches for is the radius. Shrink the kill distance by 13 px and the head-on case looks fair. That correction is right only for an enemy moving straight at you at full speed. An enemy approaching from the side, or one that has stopped, now has to visibly overlap you before it counts, and players notice that too. A radius is one number; the error is a vector that depends on speed, heading and delay. A version of the trick survives in fairtick: when no death claim arrives, the server’s fallback kills at 11 px, the 20 px distance minus 9 px of grace in the victim’s favor, and only after the reconstruction described below agrees.

The second fix is to trust the client and let the player’s device decide when it was touched. That works until someone patches the client so that it never is.

The third is the shooter approach, and it has a long pedigree. Yahn Bernier described server-side lag compensation at GDC in 2001, Valve’s Source engine has shipped it for years, and the Overwatch team talked at GDC 2017 about favoring the shooter. The server keeps a short history of positions and, when judging a hit, rewinds the world to what the shooter saw. Source doesn’t even have to guess how far back to go, because each command carries the client’s tick and its interpolation setting.

Collisions are harder, because the victim’s own dot is part of the picture, and the client predicts and smooths it in ways the server can’t reproduce exactly. I built server-side reconstruction twice anyway. Versions 4 and 5 of the death rule rebuilt the enemy the victim was looking at, projected the victim’s dot forward, and held the kill until both agreed there was contact. That was far better than the radius, but it was still a model of the screen rather than the screen. In one recorded match the server measured 3.3 px between a player and an enemy. The reconstruction put the enemy 13.7 px away on the player’s screen and the forward projection said 17.7 px, close enough to count as touching. The phone’s own log said it had drawn the enemy 23.6 px away, with no overlap at all.

If a decision depends on what a player saw, the code has to name the timeline that player saw and use it.

Ask the screen that saw it

Version 6 stopped modeling the screen and started asking it. Every kill in fairtick is one of three kinds, and each is decided on a different timeline:

Who kills youWhose timeline decides
Another playerThe attacker’s screen, through an EatClaim
A server-controlled enemyYour screen, through an EnemyDeathClaim, with a server fallback
A bot posing as a playerServer time, with conservative rules

An EatClaim is client-side hit detection with server verification, the same bargain shooters make when they favor the shooter. When your dot overlaps something it can eat, your client reports the render ticks at which it drew you and the target, the positions it drew, and the on-screen distance between them. An EnemyDeathClaim runs the other way: when a server-controlled enemy reaches you, your client reports your own death in the same terms, shows it immediately, and rolls it back if the server rejects the claim. Server-controlled enemies are a mode, and the maze arena in the repository ships with them switched off ([ai] count = 0), so a default room holds only humans and bots.

The server takes none of this on faith. It keeps a ring buffer of the last 96 ticks (1.6 seconds) recording where every entity was, and it rebuilds the claimed moment from its own history. A claim is accepted only if:

  • the reported positions agree with the reconstructed ones to within 12 px;
  • the reconstructed distance is within 26 px, the 18 px at which dots touch plus 8 px of slack for interpolation between ticks;
  • the two render ticks are no more than 54 ticks apart, which covers the client’s prediction lead plus the worst-case interpolation delay;
  • the claim arrives within 18 ticks (300 ms) of the moment it describes;
  • at that moment the target was alive, not spawn-protected or boosted, outside the safe zone, smaller than the attacker unless the attacker was boosted, and still the same life of that target (more on lives below).

Every rejection has a fixed reason string, such as too_old_after_victim_tick, that is logged and sent back to the client. The claim tolerances live in one config file whose SHA-256 hash is part of the connection handshake. That catches drift between honest builds, not cheating, since a patched client can send the right hash.

The tolerances have a price. Taken together, they let a patched client stretch its reach from 18 px to 26 px when it eats. That is the cost of accepting honest claims from phones whose rendering the server can only approximate. On the death side the risk runs the other way. Nobody forges their own death; the danger is a client that stays silent.

So the server keeps watching. Every tick it checks collisions itself, in observe-only mode, and if an enemy stays within 11 px for 30 straight ticks (half a second) while its reconstruction of the player’s screen also shows overlap, it kills without a claim and logs enemy_death_claim_missing_sustained_kill. That rules out immortality but not advantage: a client that never claims survives the brief, shallow contacts that kill an honest one.

Same ID, different life

Claims describe the past, and the past can name things that no longer exist. That caused the worst bugs in this design.

Enemies and players respawn under the same ID. A claim that arrives a few ticks late can describe an enemy that has since been eaten and reappeared somewhere else, and a careless server would validate the claim against the old position and remove the new enemy. So every entity carries a life counter (a generation for enemies, a life ID for players), every history frame records it, and a claim against life 3 cannot touch life 4.

The subtler case involves two claims about nearly the same moment. Say you eat an enemy at render tick 10. By the time your claim arrives, the server has already recorded frames 11 and 12 with that enemy alive, because until then it didn’t know. A death claim from another player at tick 11 could cite that frame and be killed by an enemy that was already dead. Sorting claims by render tick doesn’t help, because the two claims can arrive in different batches, several server ticks apart. What fixed it is a small causal ledger that remembers what each applied claim consumed, keyed by entity and life, and rejects any later claim whose premise an earlier one has already invalidated.

Making the compiler care

A rule like this survives only if you can’t break it by accident, and in a game server the accident is usually a bare number. A server tick, a fractional render tick and a Unix timestamp are all numbers, and a function that confuses them compiles fine.

In fairtick they are separate types, and every entry point into the fairness rules takes the typed version:

/// Authoritative server simulation tick. Monotonic, exactly one per `Room::update`.
#[derive(Clone, Copy, Debug, PartialEq, Eq, PartialOrd, Ord, Hash, Serialize, Deserialize)]
pub struct ServerTick(pub u64);

/// A *client* render tick — fractional, in Unity tick units. This is the timeline the
/// attacker actually saw: interpolated, `delay` ticks behind the server. Used to
/// reconstruct the attacker's view when validating an EatClaim.
#[derive(Clone, Copy, Debug, PartialEq, PartialOrd, Serialize, Deserialize)]
pub struct RenderTick(pub f64);

The wire still carries plain numbers, and the room wraps them at the boundary. There is no Deref and no arithmetic operator between the types; the few places where a server tick has to be ordered against a render tick go through a named conversion, as_render_tick, so they stand out in review. A test walks every file under src/game and fails if it finds Instant::now, SystemTime::now or .elapsed(). Telemetry can still read the clock, but every such line has to carry an // allow-wall-clock: comment saying why.

The rest of the architecture exists to keep the rules small enough to test. Each room sits behind one lock. Inputs and claims go into queues that only the tick drains, and joins and leaves take the same lock, so changes to a room happen one at a time. Most fairness decisions live in a policies module with no access to sockets, the database or the logger. Claim scheduling and the fallback still live in room.rs, the largest file in the project and the one I’d split next. Because the policies take plain inputs and return verdicts, tests/policy_scenarios.rs can replay 25 named situations, from a one-tick brush that must not kill to a stale claim after a respawn, and check both the verdict and the exact rejection reason.

Death before the snapshot

The server sends two kinds of traffic: reliable gameplay events such as deaths and respawns, and a stream of position snapshots where only the latest matters. fairtick speaks WebSocket over TLS, so on the wire everything shares one TCP connection, and a lost packet holds up whatever is queued behind it. Inside the server, though, events and snapshots come from different code paths into different queues, and a snapshot that already shows a player respawned elsewhere can overtake the event saying the player died. On screen, you teleport first and die second.

An OutboundSequencer merges both queues into one stream per player and never hands a snapshot to the socket while a reliable event is waiting. Snapshots are latest-only by construction, so a slow client skips stale frames instead of queuing them. If a player’s reliable queue overflows, the server disconnects that player rather than drop an event, and the reconnect delivers a full state.

What it costs

I measured the server on the cheapest machine I could justify: a DigitalOcean droplet with one vCPU and 2 GB of RAM, reached over the public internet through a TLS proxy. The load was 100 bots in ten 10-player rooms. The bots go through the same handshake as the real client and send input four times a second, and roughly a third of them dropped and resumed their sessions during each run. They don’t send eat or death claims, and server-controlled enemies were off, so these numbers cover simulation, history recording, snapshots and connections, not claim validation.

Tick time, 99th percentile at peak10–12 ms (budget: 16.67 ms)

An earlier ramp test, with a lighter bot load, passed at 150 players and failed at 200, so the deployment caps the server at 150 connections. Snapshots are encoded with bincode as of protocol version 6; control messages are JSON.

What isn’t solved

Bots are the biggest hole. The server fills thin rooms with bots that look like players on the wire, and a bot has no screen, so it can’t file a claim. When a bot catches a human, the kill is decided on server time with conservative rules instead: the overlap has to hold for 6 consecutive ticks, the human’s client must have finished loading the world, and protection and cooldowns apply. None of that is a guarantee. A bot chasing you at full speed is still drawn 13 px behind where the server has it, which is the scene at the top of this article. The human can’t file a death claim against it either, because the client can’t tell a bot from a person by design, and between players it is the attacker who claims.

The claim tolerances come next. A patched client can eat from 26 px instead of 18, and one that never reports its own death survives contacts that would kill an honest player until the fallback fires.

Then determinism. Gameplay randomness goes through a seeded per-room RNG, but entity IDs are random UUIDs and a few decisions depend on ID order, so replays are not bit-exact yet. The same thing made two bot tests fail about once in 35 runs until I isolated them.

Finally, this is a server with a game inside it, not a library. The rules are general; the code around them belongs to one maze game with dots that eat each other. The Unity client it was built against is not public, but you don’t need it to run the server or the load generator.

Try it

git clone https://github.com/vitaliiermolaev/fairtick
cd fairtick
cargo build --release --locked

# terminal 1: the server in local dev mode (no real sign-in), bound to localhost
FAIRTICK_DEV=1 FAIRTICK_AUTH_MODE=insecure FAIRTICK_BIND_ADDR=127.0.0.1:8080 \
  ./target/release/fairtick

# terminal 2: 100 bots for two minutes; --strict exits non-zero on any error
./target/release/bot_runner --count 100 --duration 120 --strict

While it runs, http://127.0.0.1:8080/ops shows live rooms and per-room tick times. The load run exercises the simulation and networking but not the claim rules; cargo test is where those run, starting with tests/policy_scenarios.rs and the policies in src/game/policies.

Why it’s open

I spent part of this year trying to sell this backend to studios as IP. It didn’t sell, and code like this does more good where people can read it. Much of it was written with an AI coding assistant working to the architecture rules in CLAUDE.md, which is why that file sits at the root of the repository; the design decisions, the device testing and the review notes tagged “lead review” in the comments are mine.

The open problems (bots that kill on server time, the claim tolerances, bit-exact replays) are where I’d most welcome help. If you’ve shipped victim-side validation in a real game, or tried it and backed out, I’d like to hear how it went.
